第一讲 · 目标文件格式

课件第 1–38 页

P2–3 这一讲要学什么

这一讲是整个"程序的链接"的开场。教学目标写在第 2 页：搞清楚链接器是怎么工作的。听起来好像只是工具层面的事，但它其实有两层更深的意义——一是让你养成良好的程序设计习惯、增强调试能力，二是通过"可执行文件的存储器映像"这个概念，帮你真正理解进程的虚拟地址空间。

三部分内容依次是：链接和静态链接的概念、三种目标文件格式、符号与符号表、静态库、重定位、可执行文件映像与加载，最后再讲动态链接。这一讲先把目标文件格式这个"舞台"搭好，后面两讲的符号解析、重定位都在这个舞台上进行。

一句话抓住主线：程序要跑起来，得先经历 源程序 → 可执行目标文件 的转换；链接就是这条链路的最后一环，而目标文件格式就是这一环里数据长什么样。

P4 一个典型程序的转换过程

第 4 页用经典的 hello.c 展示了完整链路。计算机不能直接执行 hello.c，因为它是给人看的 ASCII 文本。中间要经过四个步骤：

hello.c  --cpp(预处理)-->  hello.i  --cc1(编译)-->  hello.s  --as(汇编)-->  hello.o  --ld(链接)-->  hello
 源程序(文本)                 预处理后的C          汇编语言程序(文本)       可重定位目标(二进制)      可执行目标(二进制)
  • 预处理 cpp：展开 #include、#define 等，得到 hello.i；
  • 编译 cc1：翻译成汇编语言 hello.s（还是文本）；
  • 汇编 as：汇编成机器指令，得到 hello.o（二进制）；
  • 链接 ld：把 hello.o 和系统库里的 printf.o 等拼起来，得到可执行的 hello。

课件还特意放大了 hello.c 的 ASCII 编码——每个字符对应一个字节（如 #=35, i=105），就是为了让你直观感受到"文本"和"二进制"的差别。

P5–6 链接器是怎么来的

第 5、6 页讲了段很有意思的历史。最早程序员用机器语言在纸带、卡片上打孔，穿孔表示 0、未穿孔表示 1。跳转指令的目标地址只能写成绝对地址（比如"0010-jmp"跳到第 5 条）。问题来了：如果中间插入一条指令，后面所有跳转地址都要手工重算，然后重新打孔——这就是"重定位"最原始、最痛的由来。

于是人们想到：用符号代替 0/1。汇编语言用助记符表示操作码、用符号表示位置（L0、B、C）。这样只要写 jmp L0，先确定 L0 的地址，再把这个地址填进 jmp 指令就行了。高级语言出现后，程序越来越复杂、需要多人分模块开发：

  • 函数/子程序的起始地址、变量的起始地址 = 符号定义 definition；
  • 调用函数、使用变量 = 符号引用 reference；
  • 一个模块定义的符号可以被另一个模块引用，最终必须"链接（合并）"，合并时在引用处填入定义处的地址。
⭐ 核心洞察：链接器本质上干的就是两件事——找到符号定义在哪（符号解析），把地址填到引用处（重定位）。整个第 4 章都在展开这两句话。

P7 使用链接的好处

第 7 页总结两大好处：

  • 好处1：模块化。一个程序可以拆成很多源程序文件；还可以构建公共函数库（数学库、标准 I/O 库等）供所有人用。
  • 好处2：效率高。时间上——可以分开编译，改了哪个文件就只重新编译那个文件，然后重新链接即可；空间上——源文件里不用包含共享库的源码，只要直接调用，可执行文件和内存里只包含"实际调用到的"那部分库函数代码，而不是整个库。
随堂题 · P8（错误的是）
A. 使程序员可以分模块开发，提高大规模程序开发效率
B. 使公共函数库可为所有程序共享使用，利于代码重用
C. 使程序员仅需重新编译修改过的模块，节省开发时间
D. 使生成的可执行代码包含更多公共库函数代码，所占空间大
答案 D。 链接恰恰相反——只把用到的函数代码拷进来，目的就是节省空间；"包含更多库代码、空间大"与链接的初衷相悖。A/B/C 都是链接公认的好处。

P9–10 贯穿全课的示例程序

从第 9 页开始，课件引入了一个会贯穿后面所有讲解的例子——main.c 和 swap.c。务必记住它，后面符号表、重定位都围着它转。

/* main.c */
int buf[2] = {1, 2};          // 定义全局数组 buf
void swap();                  // 声明（引用）外部函数 swap
int main() { swap(); return 0; }

/* swap.c */
extern int buf[];              // 引用别处定义的 buf
int *bufp0 = &buf[0];           // 定义并初始化全局指针 bufp0
static int *bufp1;             // 定义静态（本地）指针 bufp1
void swap() {
    int temp;                     // 局部变量，分配在栈上，不是符号
    bufp1 = &buf[1];
    temp = *bufp0;  *bufp0 = *bufp1;  *bufp1 = temp;
}

课件问："哪些是符号定义？哪些是引用？"注意最后那句提示——局部变量 temp 分配在栈上，不会在过程外被引用，因此不是符号。这一点在第二讲会反复强调。

第 10 页给出编译命令：gcc -O2 -g -o p main.c swap.c。-O2 是 2 级优化，-g 生成调试信息（后面会看到它多产出 .debug 和 .line 节），-o p 指定输出文件名。静态链接过程是：两个 .c 分别经过 cpp/cc1/as 变成 main.o 和 swap.o，再由 ld 链接成可执行文件 p。

P11 链接的本质：合并相同的"节"

第 11 页是理解全局的关键图。链接器把多个可重定位目标文件里相同的"节"(section) 合并到一起，形成可执行文件：

  • main.o 的 .text（main 的代码）+ swap.o 的 .text（swap 的代码）+ 系统代码 → 可执行文件的一个大 .text 节；
  • 各自的 .data（buf、bufp0）合并成一个 .data 节；
  • 各自的 .bss（bufp1）合并成一个 .bss 节；
  • ELF 头、系统数据、.symtab、.debug 等也一并整合。
记住这句话：链接 = 合并相同的节 + 给符号定地址 + 改写引用。第 11 页讲"合并节"，第 14–15 页讲完整四步，第三讲再逐步算给你看。

P12 从 objdump 看"重定位前 vs 后"

第 12 页用 objdump -d 反汇编对比了同一个 add 函数在两种文件里的样子：

  • 在可重定位文件 test.o 里，add 的地址是 0 开始的相对偏移（00000000 <add>:，指令从 0、1、3…编号）；
  • 在可执行文件 test 里，add 已经有了真实的虚拟地址（080483d4 <add>:）。

两条指令的机器码字节完全一样，只是地址标签变了。这正好说明：.o 文件里的代码和数据地址都从 0 开始，链接后被重新安置到虚拟地址空间的某个位置——这就是"重定位"名字的由来。

P13 可执行文件的存储器映像

第 13 页第一次展示了一张后面会反复出现的图——32 位 Linux 进程的虚拟地址空间布局。从低地址到高地址依次是：

  • 0x08048000 起：从可执行文件装入的只读代码段（.init/.text/.rodata）和读写数据段（.data/.bss）；
  • 堆 heap：由 malloc 动态生成，向上增长，顶端是 brk；
  • 共享库区域：动态链接的 .so 映射在这里；
  • 用户栈 User stack：动态生成，顶端是 %esp，向下增长；
  • 0xC0000000 以上：内核虚存区（1GB）。

图的左侧还画了可执行文件本身的节，并注明"程序(段)头表描述如何映射"——也就是文件的节是怎么被搬到内存各段去的。这张图现在是"先混个脸熟"，第 33、36 页会详细讲。

P14–15 链接操作的完整步骤

这两页把链接拆成四小步（第 14 页），第 15 页又归并成两大步，务必记牢：

  1. 确定标号引用关系（符号解析）——把每个符号引用和某个确定的符号定义关联起来；
  2. 合并相关 .o 文件——把多个代码段、数据段分别合并成一个；
  3. 确定每个标号的地址——计算每个定义符号在虚拟地址空间中的绝对地址；
  4. 在指令中填入新地址——把引用处的地址改成重定位后的地址。

第 15 页把它归纳成两步：Step 1 符号解析（Symbol resolution） 和 Step 2 重定位（Relocation）。符号表是个结构数组，每个表项含符号名、长度、位置等；编译器把定义的符号存进符号表，链接器把每个引用和确定的定义建立关联。第二讲专讲 Step 1，第三讲专讲 Step 2。

P16–17 三类目标文件与常见格式

第 16 页讲三种目标文件：

类型说明扩展名
可重定位目标文件代码数据可与其他 .o 合并；由对应 .c 生成；地址都从 0 开始.o（Windows 是 .obj）
可执行目标文件代码数据可被直接复制到内存执行；地址是虚拟地址默认 a.out（Windows .exe）
共享目标文件特殊的可重定位文件，装入或运行时被装入并自动链接.so（Windows 叫 DLL）

第 17 页回顾目标文件格式的历史：DOS 的 COM（最简单，只有代码数据、加载到固定位置）→ System V UNIX 的 COFF（含重定位、调试、符号表等信息）→ Windows 的 PE（COFF 变种）→ Linux 的 ELF（COFF 变种，Executable and Linkable Format）。本课程聚焦 ELF。

P18 ELF 的两种视图（重点）

第 18 页是 ELF 的核心概念——同一份 ELF 文件，站在不同角度有两种看法：

  • 链接视图（被链接时）：对应可重定位目标文件，由不同的节 section 组成。节是 ELF 文件中具有相同特征的最小可处理单位，比如 .text 是代码、.data 是数据、.rodata 是只读数据、.bss 是未初始化数据。
  • 执行视图（被执行时）：对应可执行目标文件，由不同的段 segment 组成。段描述节如何映射到存储段，多个节可以映射到同一个段——例如 .data 和 .bss 合并映射到一个"可读可写数据段"。
⭐ 这是选择题高频考点：节（section）是链接的视角，段（segment）是执行的视角。可重定位文件=链接视图=按节组织；可执行文件=执行视图=按段组织。

P19–22 可重定位目标文件：各节详解

第 19 页先总述：可重定位文件能被链接生成可执行或共享文件，静态库就是由若干个 .o 组成的，它包含代码、数据（已初始化 .data 和未初始化 .bss），还包含重定位信息（指出哪些符号引用处需要重定位）。第 20–22 页逐节介绍，这是必须掌握的表格：

节名作用
ELF 头魔数、版本、大小端、OS 平台、文件类型、机器类型、节头表起始位置和长度等
.text编译后的机器代码
.rodata只读数据，如 printf 格式串、switch 跳转表
.data已初始化的全局变量
.bss未初始化全局变量，仅是占位符，不占实际磁盘空间（区分初始化/未初始化是为了空间效率）
.symtab符号表，函数名和全局静态变量名等信息
.rel.text.text 相关的重定位信息：合并时哪些指令的操作数地址/跳转目标要改
.rel.data.data 相关的重定位信息：合并时哪些全局变量地址要改
.debug调试符号表，只有 gcc 带 -g 才有
.strtab字符串表：.symtab 和 .debug 中的符号名、节名，以 null 结尾的字符串序列
.lineC 源程序行号与 .text 机器指令的映射，也要 -g 才有
节头表若干表项，每项描述一个节的节名、偏移、大小、访问属性、对齐方式等

P23–24 .rodata 的两个例子

第 23 页：函数里的字符串 "x=%d\n" 属于只读数据，放在 .rodata 节。
第 24 页：switch-case 语句，编译器会生成一张跳转表，这张表也放在目标文件的只读节中，按 4 字节边界对齐。原理是：先把 a 减去最小值（R[eax]=a-10=i），判断 if (a-10)>7 就越界转 default，否则用 .L8 + 4*i 查表直接跳到对应 case——这就是 switch 比一长串 if-else 高效的原因。

随堂题 · P25（错误的是）
A. .text 节包含相应模块内所有机器代码
B. .data 节包含相应模块内所有变量的初始值
C. .rodata 节包含相应模块内所有只读数据
D. .rel.text 和 .rel.data 包含相应节内所有可重定位信息
答案 B。 .data 只放已初始化的全局变量：未初始化的全局变量在 .bss，局部变量在栈上，都不在 .data。"所有变量的初始值"这个说法范围过大，故错误。

P26–29 ELF 头与节头表：读 readelf 输出

第 26 页用 readelf -h main.o 展示可重定位文件的 ELF 头，重点字段：

  • Magic 魔数：7f 45 4c 46，即 ASCII 的 \x7f ELF，用来识别这是 ELF 文件；
  • Class ELF32、Data 小端（little endian）、OS/ABI UNIX-System V；
  • Type: REL（可重定位文件）；Machine: Intel 80386；
  • Entry point address: 0x0——可重定位文件没有入口地址；
  • Start of program headers: 0，程序头表大小为 0——说明可重定位文件没有程序头表；
  • Start of section headers: 516，节头表每表项 40 字节，共 15 项（15×40=600B）。

第 27 页给出节头表表项结构 Elf32_Shdr（32 位下每项 40B），关键字段：sh_name（节名在 .strtab 的偏移）、sh_type（节类型）、sh_flags（访问属性 W 写/A 分配/X 执行）、sh_addr（可装入时的虚拟地址）、sh_offset（文件中偏移，.bss 无意义）、sh_size（节长度）、sh_link/sh_info（与链接相关的节用）、sh_addralign（对齐）、sh_entsize（表项长度）。

第 28–29 页用 readelf -S test.o 展示真实节头表：11 个节，.text 的 Flg=AX（可分配+可执行），.data/.bss 是 WA（可写+可分配），.rodata 是 A（只读）。并且强调可重定位文件中每个可装入节的起始地址（Addr）总是 0。

P30–32 可执行目标文件：和可重定位文件的区别

第 30 页：可执行文件包含代码和数据，所有变量和函数都已有确定的虚拟地址，符号引用处已被重定位，没有扩展名（默认 a.out），可被 CPU 直接执行。为了能执行，还要把具有相同访问属性的节合并成段（Segment），并说明每个段的属性，这就是程序头表（段头表）的作用。

第 31 页列出可执行文件相对可重定位文件的四点不同（选择题常考）：

  1. ELF 头的 e_entry 字段给出第一条指令的地址（可重定位文件中为 0）；
  2. 多一个程序头表（段头表），是结构数组；
  3. 多一个 .init 节，定义 _init 函数做执行前的初始化；
  4. 少两个 .rel 节（已经重定位完，不再需要）。

第 32 页 readelf -h main 印证：Type 变成 EXEC，Entry point = 0x8048580，程序头表有 8 个表项（8×32B），节头表 29 项。

P33–36 存储器映像与程序头表

第 33 页：可执行文件与虚拟地址空间的存储器映像（memory mapping）由 ABI 规范定义（i386 System V ABI）。这张图和第 13 页基本一致，只是加上了具体地址。可执行文件只有 4 个节会分配（A）空间：.text 可执行、.data/.bss 可读写、.rodata 只读；.symtab/.debug/.line/.strtab 这些调试信息不会装入内存。

第 34–35 页讲程序头表（Elf32_Phdr，每项 32B），它描述文件的节与虚拟空间存储段之间的映射关系。8 个表项里有 2 个是可装入段（Type=LOAD）：

  • 第一可装入段（只读代码段）：文件第 0x0~0x4d3 字节（ELF 头+程序头表+.init+.text+.rodata），映射到虚拟地址 0x8048000 开始、长度 0x4d4 的区域，按 4KB 对齐，权限 RE（只读+执行）；
  • 第二可装入段（读写数据段）：文件第 0xf0c 起的 .data（0x108B），映射到 0x8049f0c 开始、长度 0x110 的区域；前 0x108B 用 .data 内容初始化，后 8B 是 .bss 初始化为 0，权限 RW（可读可写）。
⭐ 注意"文件内容大小"和"内存大小"的差别：.bss 在文件里不占空间，但在内存里会被分配并清零——这正是 .bss 存在的意义。
随堂题 · P37（错误的是）
A. 可重定位文件的 ELF 链接视图，由不同的节组成
B. 可执行目标文件是 ELF 执行视图，由不同的段组成
C. 可重定位和可执行目标文件中的数据都是二进制补码形式
D. 两种目标文件中的代码都是二进制指令形式
参考答案 C。 A、B 正是"两种视图"的正确表述，D 也正确（代码都是机器指令）。C 的问题在于"数据都是补码"过于绝对：整型数值确实以补码表示，但浮点数用 IEEE 754、字符/字符串用 ASCII、地址是指针值，不能一概说"都是补码"。（此题重在理解两种视图与数据表示的区别。）

第一讲小结（P38）

这一讲搭好了舞台：程序的链接概述、意义与过程，以及三种目标文件格式——ELF 可重定位文件（链接视图，按节组织）和 ELF 可执行文件（执行视图，按段组织）。核心结论：链接就是合并相同的节、给符号定地址、改写引用；.o 里地址从 0 开始，链接后变成虚拟地址。下一讲开始处理"符号"这件事。

LECTURE TWO

第二讲 · 符号表与符号解析

课件第 39–77 页

P40–42 三种链接器符号

第 41 页：每个可重定位目标模块 m 都有一个符号表，包含 m 中定义的符号。链接器关心三种符号：

  • Global symbols 全局符号：由模块 m 定义、能被其他模块引用。例如非 static 的函数和非 static 的全局变量（如 main.c 里的 buf）。
  • External symbols 外部符号：由其他模块定义、被模块 m 引用。例如 main.c 里的函数名 swap。
  • Local symbols 本地符号：仅由模块 m 定义和引用，例如带 static 的函数和全局变量（如 swap.c 里的 bufp1）。
⚠ 最容易踩的坑：链接器说的"本地符号"不是 C 语言里的"局部变量"！局部变量分配在栈上、是临时性的，根本不进符号表。课件第 41 页 L3 和第 42 页结尾都特意强调了这点。

第 42 页让你对 main.c / swap.c 分类：buf、bufp0、main、swap 是全局符号（其中 swap 在 main.c 里是外部引用）；bufp1 是本地符号；temp 是局部变量，不是符号。

P43–44 符号表的结构（Elf32_Symbol）

第 43 页：.symtab 节记录符号表，是一个结构数组。函数名在 .text 节，变量名在 .data 或 .bss 节。每个条目结构如下：

typedef struct {
    Elf32_Word    st_name;    /* 符号名在 .strtab 中的偏移 */
    Elf32_Addr    st_value;   /* 在对应节中的偏移；可执行文件中是虚拟地址 */
    Elf32_Word    st_size;    /* 符号占的字节数 */
    unsigned char st_info;    /* 低4位=类型(未指定/变量/函数/节)，高4位=绑定(本地/全局/弱) */
    unsigned char st_other;   /* 可见性，均为 0 */
    Elf32_Section st_shndx;   /* 所在节：1=.text, 3=.data，或特殊值 */
} Elf_Symbol;

特殊的 st_shndx 值：ABS 表示不该被重定位；UND 表示未定义（在别的模块）；COM 表示未初始化数据（.bss），此时 value 是对齐要求，size 是最小大小。

第 44 页给出真实符号表（readelf -s 风格）：

/* main.o 的最后三个条目（共10个） */
8: 0  8  Object Global  3    buf      // .data 节偏移0，全局对象，占8B
9: 0  33 Func   Global  1    main     // .text 节偏移0，全局函数，占33B
10: 0  0  Notype Global  UND  swap     // 未定义全局符号，类型大小未知

/* swap.o 的最后四个条目（共11个） */
8: 0  4  Object Global  3    bufp0    // .data 节偏移0，占4B
9: 0  0  Notype Global  UND  buf      // 未定义，来自 main.o
10: 0 36 Func   Global  1    swap     // .text 节偏移0，占36B
11: 4  4  Object Local   COM  bufp1    // 本地，未分配未初始化，4B对齐，占4B
这张表后面还会用：swap 在 main.o 里是第 10 项，buf 在 swap.o 里是第 9 项。第三讲算重定位时，"r_sym=10 说明引用的是 swap"、"r_sym=9 说明引用的是 buf"，依据就在这里。
随堂题 · P46（错误的是）
A. 由模块 m 定义并能被其他模块引用的符号称为 m 的全局符号
B. 由其他模块定义并被 m 引用的称为 m 的外部符号
C. 由 m 定义并仅在 m 中引用的称为 m 的本地符号
D. 在模块 m 内某个函数中定义的局部变量称为 m 的局部符号
答案 D。 局部变量分配在栈上，不进符号表，不是链接器的局部（本地）符号。A/B/C 正是三类链接器符号的准确定义。

P48–50 强符号与弱符号

第 48 页抛出一个问题：main.c 里 int x=10;，p1.c 里 int x=20;，会链接出错吗？带着这个问题往下看。

第 49 页讲符号解析的目的：把每个模块中引用的符号与某个目标模块中的定义符号建立关联。局部符号解析简单（本模块内唯一定义），全局符号涉及多个模块，较复杂。这里有个关键定义——"符号的定义"实质是被分配了存储空间（函数名→代码区，变量名→静态数据区），所有定义符号的值就是其目标所在的首地址。符号解析也叫符号绑定。

第 50 页给出强弱规则：

  • 强符号：函数名 + 已初始化的全局变量名；
  • 弱符号：未初始化的全局变量名；
  • 外部符号（UND 引用）没有强弱之分。

所以 p1.c 的 int var=5; 是强符号，p2.c 的 int var; 是弱符号。

P51–54 弱符号的声明与用法

第 51 页对 main.c / swap.c 逐个判断强弱：buf[2]={1,2} 是强符号，bufp0=&buf[0] 已初始化也是强符号，swap() 函数定义是强符号；而 bufp1 是本地局部符号、temp 是局部变量——它们不参与强弱讨论；main.c 里对 buf、swap 的引用是外部引用，也无强弱。

第 52–54 页演示了 GCC 的弱符号扩展：__attribute__((weak)) 可以把一个函数声明成弱符号：

void __attribute__((weak)) swap();   // 把 swap 声明为弱符号
...
if (swap) swap();                       // 先判断是否为 NULL 再调用

这样即使链接时没有 swap 的定义（引用的弱符号值为 0/NULL），程序也不会崩溃——if(swap) 判断为假就直接跳过。这是插件式、可选功能设计的常用技巧。

P55 链接器的符号解析三规则（核心考点）

第 55 页给出三条规则，前提是"符号解析时只能有一个确定的定义（每个符号仅占一处存储空间）"：

  1. Rule 1：强符号不能多次定义——强符号只能定义一次，否则链接错误；
  2. Rule 2：一强多弱，取强——若一个符号被定义为一次强符号和多次弱符号，按强定义为准，对弱符号的引用被解析为对强符号的引用；
  3. Rule 3：多个弱符号，任选一个——若有多个弱符号定义，任选其一。用 gcc -fno-common 链接时，遇到多个弱定义的全局符号会输出警告。
⭐ 三条规则一定要能背下来，并会用来判断程序是否链接出错、打印结果是什么。第 56–58 页就是三个实战例子。

P56–58 多重定义的三个例子

例1（P56）：回到开头的问题——main.c 的 int x=10; 和 p1.c 的 int x=20;。main 只有一次强定义，p1 有一次强定义，但 x 有两次强定义，违反 Rule 1，链接器报错。

例2（P57）：main.c 里 int y=100; int z;，p1.c 里 int y; int z;。分析：y 是"一强一弱"→按 Rule 2 取强的（main.c 的 y=100）；z 是"两次弱定义"→按 Rule 3 任选一个存储位置，两处引用都指向它。p1() 里执行 y=200; z=2000;，所以最终打印 y=200，z=2000。这个例子说明：在两个不同模块定义相同变量名，很可能发生意想不到的结果——你以为是两个变量，其实链接后是同一个！

例3（P58）：更隐蔽。main.c 里 int d=100; int x=200;（d 是 int），p1.c 里 double d;（d 是 double，未初始化=弱）。d 一强一弱按强的，所以是 int 型、占 4 字节；但 p1() 执行 d=1.0 时用的是 FSTPl &d——这是双精度存储指令，写 8 字节！于是把 d 后面的 4 字节（正好是 x）也覆盖了。1.0 的 double 编码是 0x3FF0000000000000，低 4 字节 00000000 写入 d，高 4 字节 3FF00000（十进制 1072693248）写入 x。所以打印 d=0，x=1072693248。这个例子说明：两个重复定义且类型不同的变量，更容易产生难以理解的结果。

⚠ 这正是"链接知识有啥用"的最好回答：这类错误编译时不会有任何警告，程序可能跑很久才在某个莫名其妙的地方出错，且错误现象离真正的原因十万八千里。不了解链接器，你根本无从查起。

P59 符号定义的注意事项

第 59 页给出编程建议：

  • 尽量避免使用全局变量；
  • 一定要用就遵守规则：尽量用 static（本地化）、全局变量要赋初值（成为强符号、可控）、外部全局变量要用 extern 声明。

课件强调：多重定义全局变量造成的错误是默默发生的——编译系统不警告，程序执行很久后才表现，且远离错误引发处。在几百个模块的大型软件里极难修正。所以大部分程序员不了解链接器，而你要养成好习惯。

随堂题 · P61（错误的是）
A. 局部符号没有强弱符号的概念
B. 所有出现的函数名都是强符号
C. 没有初始化的全局变量名是弱符号
D. 已初始化的全局变量名是强符号
答案 B。 "出现"的函数名不一定是定义——extern 声明的函数只是外部引用（UND），没有强弱；用 __attribute__((weak)) 声明的函数也可以是弱符号（第 53 页）。A/C/D 都符合定义。
随堂题 · P62（错误的是）
A. 一个符号名只能有一个强符号，否则符号解析失败
B. 一个符号名可以有多个弱符号，任选一个为其定义
C. 一个符号名可以有一个强符号和多个弱符号，强符号为其定义
D. 一个符号名可以仅出现在引用处或仅出现在定义处
答案 D。 若一个符号仅出现在引用处、没有任何模块定义它，链接就会报 "undefined reference" 错误（弱引用除外）。A/B/C 正是解析三规则的复述。

P64–68 静态共享库（.a 归档文件）

第 64 页先抛出场景：func.o 调用 libx.a 和 liby.a 中的函数，libx.a 又调用 libz.a，而 libx.a 与 liby.a 之间、liby.a 与 libz.a 相互独立——该怎么链接？这就是"库"的问题。

第 65 页：静态库（.a archive files）就是把所有相关的目标模块（.o）打包成一个单独的库文件，也叫存档文件 archive。它增强了链接器功能——链接器能通过查找库文件中的符号来解析符号。构建可执行文件时只需指定库文件名，链接器会自动到库中寻找应用程序用到的目标模块，只把用到的模块拷贝出来。C 标准库 libc.a 是默认库，gcc 命令行无需显式指定。

第 66 页讲创建：ar rcs libc.a atoi.o printf.o ... random.o。归档器 ar 允许增量更新——只重新编译修改的源码、把新 .o 替换进库即可。

第 67 页列常用库：libc.a（C 标准库，约 1392 个目标文件、8MB，含 I/O、存储分配、信号处理、字符串、时间日期、随机数、定点整数运算）；libm.a（数学库，约 401 个目标文件、1MB，含 sin/cos/tan/log/exp/sqrt 等浮点运算）。

第 68 页自定义库示例：把 myproc1.o、myproc2.o 打包成 mylib.a，gcc -c main.c 后 gcc -static -o myproc main.o ./mylib.a，调用关系是 main→myfunc1→printf。问题：符号解析怎么进行？

P69–71 符号解析全过程：E / U / D 三集合算法（重点）

这是第二讲最重要的算法。链接器维护三个集合：

  • E：将被合并以组成可执行文件的所有目标文件集合；
  • U：当前所有未解析的引用符号集合；
  • D：当前所有已定义符号集合。

以 main→myfunc1→printf 为例，从头走一遍：

  1. 初始 E、U、D 为空。扫描 main.o：加入 E；main 进 D；myfunc1 进 U。
  2. 扫描 mylib.a：把 U 中的符号（myfunc1）和库中所有模块（myproc1.o、myproc2.o）依次匹配，发现 myproc1.o 定义了 myfunc1 → myproc1.o 加入 E，myfunc1 从 U 移到 D。myproc1.o 里又引用了 printf → printf 进 U。不断迭代直到 U、D 不再变化。此时 U 只剩 printf，而 myproc2.o 没被加入 E，被丢弃。
  3. 扫描默认库 libc.a：printf.o 定义了 printf → printf 从 U 移到 D，printf.o 加入 E，同时把它定义的符号加入 D、它引用的未解析符号加入 U。处理完 libc.a 时，U 一定是空的，D 中符号唯一。

最终结果（P70）：E 中有 main.o、myproc1.o、printf.o 及其调用的模块；D 中有 main、myfunc1、printf 及其引用符号。注意 E 中没有 myproc2.o——这就是静态库"只取所需"的精髓。

⭐ 这个 E/U/D 算法要能自己推演。它直接解释了下一页的"链接顺序问题"。

P71–73 链接顺序问题（高频考点）

第 71 页：如果把命令写成 gcc -static -o myproc ./mylib.a main.o（库放在 .o 前面），结果怎样？

  • 先扫描 mylib.a，此时 U 为空——链接器认为没有任何符号需要解析，于是 myproc1.o 和 myproc2.o 都被丢弃；
  • 再扫描 main.o，把 myfunc1 加入 U，但此后没有库了，myfunc1 始终无法解析；
  • → 链接错误！因为它只能用 mylib.a 里的符号解析，而库里的 .o 已经被丢弃了。

第 72 页总结链接器对外部引用的解析算法要点：按命令行顺序扫描 .o 和 .a；扫描中把未解析引用记入 U；每遇到一个新模块就试图用它解析 U 中的符号；扫到最后 U 还有符号就出错。对策：能否正确解析与命令行顺序有关，好的做法是把静态库放在命令行最后。

第 73 页给出库间依赖的顺序规则：

  • 若 libx.a→libz.a，且 libx.a、liby.a 独立：以下都行——func.o libx.a liby.a libz.a、func.o liby.a libx.a libz.a、func.o libx.a libz.a liby.a（原则：被调用的库排在调用者后面）。
  • 若 libx.a 和 liby.a 相互依赖：要重复写库——func.o libx.a liby.a libx.a 或 func.o liby.a libx.a liby.a。

P74 如何划分模块

第 74 页：许多函数无需自己写，用共享库即可（数学库、I/O 库、存储管理、字符串处理）。要避免两种极端：所有函数放一个源文件（改一个函数要重编全部，时间和空间效率都低）和一个源文件只放一个函数（模块太多太繁琐、需显式链接）。要折中。

随堂题 · P76（能正确静态链接的命令）

条件：func1.o→func2.o，func1.o→libx.a，func2.o→libx.a，libx.a ⇄ liby.a 相互依赖。

A. gcc -static -o myfunc func1.o func2.o libx.a liby.a libx.a
B. gcc -static -o myfunc func2.o func1.o liby.a libx.a liby.a
C. gcc -static -o myfunc libx.a liby.a libx.a func1.o func2.o
D. gcc -static -o myfunc liby.a libx.a liby.a func1.o func2.o
答案 A。 两条原则：① .o 必须在库前（C、D 把库放最前，扫描库时 U 为空，全被丢弃，错）；② 库内部 libx.a 被 func1.o/func2.o 直接依赖，必须先扫 libx.a，且相互依赖要重复成 libx.a liby.a libx.a。A 完全符合。B 把 liby.a 放最前，第一次扫描时 U 里还没有 liby 的符号，会被丢弃，结尾又缺 libx.a 兜底，故不正确。

第二讲小结（P75–77）

三件事：① 三类符号（全局/外部/本地，注意本地≠局部变量）；② 强弱特性（函数名和已初始化全局变量是强符号，未初始化全局变量是弱符号，解析三规则）；③ 符号解析过程（E/U/D 算法、静态库、库放最后、相互依赖的库要重复写）。下一讲解决链接的第二大步——重定位。

LECTURE THREE

第三讲 · 重定位与动态链接

课件第 78–108 页

P79–81 重定位的三步

第 80 页用前面的符号程序回顾了链接四件事：符号绑定、同节合并、确定地址、修改引用。第 81 页正式给出符号解析完成后，重定位分三步：

  1. 合并相同的节：把集合 E 中所有目标模块里相同的节合并成新节（所有 .text 合成一个 .text）；
  2. 对定义符号重定位（确定地址）：确定新节中所有定义符号在虚拟地址空间中的地址——为函数定首地址进而定每条指令地址，为变量定首地址；完成后每条指令和每个全局变量都有地址；
  3. 对引用符号重定位（修改引用）：修改 .text 和 .data 中对每个符号的引用（地址），要用到 .rel_data 和 .rel_text 节中的重定位信息。

P82 重定位信息与两种重定位类型

第 82 页：汇编器遇到引用时就生成一个重定位条目。数据引用的条目在 .rel_data 节，指令中引用的在 .rel_text 节。条目格式：

typedef struct {
    int offset;              /* 节内偏移：要修改的位置 */
    int symbol : 24,        /* 所绑定的符号 */
        type   : 8;         /* 重定位类型 */
} Elf32_Rel;

IA-32 有两种最基本的重定位类型：

  • R_386_32：绝对地址方式；
  • R_386_PC32：PC 相对地址方式。

课件举例：在 .rel.text 中有条目 offset=0x1, symbol=B, type=R_386_32；另有 offset=0x6, symbol=L0, type=R_386_PC32。课件随堂问："重定位条目和汇编后的机器代码在哪种目标文件里？" 答案是在可重定位目标（.o）文件里。

⚠ 易错：第 98 页的随堂题就考这里——重定位条目是汇编器 as 在汇编时产生的，不是编译器！

P83–88 例：main.o 中对 swap 的重定位（R_386_PC32）

回到 main.c / swap.c。第 84 页：符号解析后 E 中有 main.o 和 swap.o（没有 printf.o，因为没调用 printf），D 中有所有定义符号。用 readelf -r main.o 看重定位条目。

第 86 页反汇编 main.o 的 .text：

00000000 <main>:
  0: 55              push   %ebp
  1: 89 e5           mov    %esp,%ebp
  3: 83 e4 f0        and    $0xfffffff0,%esp
  6: e8 fc ff ff ff  call   7 <main+0x7>
          7: R_386_PC32  swap     // ← call 的操作数 0xfffffffc = -4 要被改
  b: b8 00 00 00 00  mov    $0x0,%eax
 10: c9              leave
 11: c3              ret

指令在节内偏移 0x6 处调用 swap，操作数是 -4（初始占位值）。重定位条目为 r_offset=0x7, r_sym=10, r_type=R_386_PC32——第 87 页提醒：r_sym=10 正是 main.o 符号表里 swap 的编号，说明引用的是 swap。

第 88 页详细计算（重点）：假定可执行文件中 main（18 字节=0x12）从 0x8048380 开始，swap 紧跟其后按 4 字节对齐 → swap 起始地址 = 0x8048380+0x12 = 0x8048392，对齐后是 0x8048394（中间补两条 nop）。

  • call 指令的下一条指令地址（即执行时的 PC）= 0x8048380 + 0x07 − (−4) = 0x804838b（注意那个 −4 是机器码里的初始占位值 init）；
  • 重定位值 = 转移目标 − PC = 0x8048394 − 0x804838b = 0x9；
  • 所以 call 的机器码从 e8 fc ff ff ff 改成 e8 09 00 00 00。
PC 相对方式重定位值公式：
ADDR(r_sym) − ( ( ADDR(.text) + r_offset ) − init )
其中 ADDR(.text)+r_offset−init = call 下一条指令地址 = 当前 PC

P89–92 例：swap.o 中对 buf 的重定位（R_386_32）

第 90 页看 .data 节。main.o 的 buf 定义在 .data 偏移 0 处、占 8B（内容 01 00 00 00 02 00 00 00），没有需重定位的符号。swap.o 里 bufp0 = &buf[0] 定义在 .data 偏移 0、占 4B，初值是 0x0（占位），因为 buf 是外部符号，这里需要重定位：

00000000 <bufp0>:
  0: 00 00 00 00
        0: R_386_32  buf    // r_offset=0x0, r_sym=9, r_type=R_386_32

第 91 页提醒：r_sym=9 是 swap.o 符号表里 buf 的编号，说明引用的是 buf。

第 92 页计算：假定合并后 ADDR(buf)=0x8049620。buf 和 bufp0 同属 .data，被合并，bufp0 紧跟 buf 之后 → bufp0 地址 = 0x8049620+8 = 0x8049628。因为是 R_386_32（绝对地址），bufp0 的内容被改成 buf 的绝对地址 0x8049620，小端存储即字节 20 96 04 08。

绝对地址方式：重定位值 = ADDR(定义符号) + 占位值(init，通常为 0)
R_386_32 直接填入符号的绝对地址；R_386_PC32 填入「目标地址 − 当前PC」的差值。

P93–94 swap.o 的六处重定位

第 93 页反汇编 swap.o 的 .text，标出共 6 处需要重定位（偏移 8、c、11、1b、21、2a）。第 94 页逐一算出填入值：

  • 已知：buf=0x8049620，bufp0=0x8049628，&buf[1] = 0x8049620+4 = 0x8049624，bufp1 是 .bss 首地址，假定 0x8049700；
  • 8 处（bufp1 地址）→ 00 97 04 08
  • c 处（&buf[1]）→ 24 96 04 08
  • 11 处（bufp0）→ 28 96 04 08
  • 1b 处（bufp0）→ 28 96 04 08
  • 21 处（bufp1）→ 00 97 04 08
  • 2a 处（bufp1）→ 00 97 04 08
⭐ 第 85 页还特别强调：虽然 bufp1 是 swap 的本地符号，也需要在 .bss 节重定位——因为 .o 里的地址都是相对的，合并成可执行文件后都要换成真实地址，本地符号也不例外。

P95 重定位后的完整代码

第 95 页给出最终可执行文件中的样子。main 中 call 已经指向真实的 swap 地址：

08048380 <main>:
 8048386: e8 09 00 00 00   call   8048394 <swap>   // 已重定位！
 8048392: 90  nop
 8048393: 90  nop                              // 4字节对齐填充

08048394 <swap>:
 804839a: c7 05 00 97 04 08 24 96 04 08   movl $0x8049624, 0x8049700   // bufp1=&buf[1]
 80483a4: a1 28 96 04 08        mov 0x8049628, %eax    // temp=*bufp0
 80483b3: 8b 15 00 97 04 08     mov 0x8049700, %edx    // *bufp0=*bufp1
 80493bd: a1 00 97 04 08        mov 0x8049700, %eax    // *bufp1=temp

课件还要求写出 call 指令的功能描述（R[eip] 此时=0x804838b）：① R[esp]←R[esp]−4（压栈）；② M[R[esp]]←R[eip]（把返回地址压栈）；③ R[eip]←R[eip]+0x9（跳到 swap）。这正是 call 的语义。

重定位小结（P96）

三步：同节合并 → 确定地址 → 修改引用。两种类型：R_386_32（绝对地址，填符号真实地址）、R_386_PC32（PC 相对，填「目标−当前PC」的差值）。

随堂题 · P97（错误的是）
A. 重定位的最终目标是重新确定各模块合并后每个引用所指向的目标地址
B. 重定位第一步应先将相同节合并，且将具有相同存储属性的节合并成段
C. 第二步是确定每个段的起始地址，并确定段内每个定义处符号的地址
D. 最后一步是将引用处的地址修改为关联定义处的首地址
参考答案 B。 重定位第一步是"合并相同的节"；而"把具有相同存储属性的节合并成段"是为生成可执行文件执行视图而做的段映射（程序头表的工作），把它说成重定位的步骤不够准确。A/C/D 都是对重定位三步和目标的正确描述。
随堂题 · P98（错误的是）
A. 重定位信息是由编译器在生成汇编指令时产生的
B. 指令中的重定位信息在可重定位目标文件的 .rel.text 节中
C. 数据中的重定位信息在可重定位目标文件的 .rel.data 节中

答案 A。 课件第 82 页明确："汇编器遇到引用时，生成一个重定位条目"。是 as 在汇编阶段产生，不是编译器 cc1。B/C/D 分别对应 .rel.text、.rel.data 和 Elf32_Rel 三个字段（offset/symbol/type），均正确。

P100–101 为什么要动态链接：静态库的缺点

第 100 页回顾静态库。第 101 页指出静态库的三个缺点：

  1. 库函数（如 printf）被包含进每个运行进程的代码段——上百个进程并发时，主存里就有上百份 printf，极大浪费内存；
  2. 库函数被合并进每个可执行文件——磁盘上几千个可执行文件各带一份，极大浪费磁盘；
  3. 库更新困难——程序员要关注新版本、下载、重新编译链接，使用不便。

解决方案是共享库 Shared Libraries：它也是一个含代码数据的目标文件，但从程序中分离出来，磁盘和内存中都只有一份备份，可以动态地在装入时或运行时加载链接。Windows 叫动态链接库 .dll，Linux 叫动态共享对象 .so。

P102 动态链接的两种方式

第 102 页：动态链接有两种时机：

  • 装入时链接（load-time linking）：第一次加载并运行时进行，Linux 通常由动态链接器 ld-linux.so 自动处理，标准 C 库 libc.so 通常按这种方式；
  • 运行时链接（run-time linking）：程序已经开始运行后进行，Linux 通过 dlopen() 等接口实现，用于分发软件包、构建高性能 Web 服务器等。

共享库的好处：内存中只有一份备份被所有进程共享（省内存）；一个 .so 文件被所有程序共享（省磁盘）；升级时自动加载、程序动态链接（方便）；可分模块、用不同语言开发（效率高）；第三方共享库可作插件，功能易扩展。

P103 位置无关代码 PIC

第 103 页：动态链接用到一个重要概念——位置无关代码（Position-Independent Code, PIC），GCC 用 -fPIC 选项生成。共享库代码就是 PIC：它的位置可以是不确定的，即使长度变化也不影响调用它的程序。引入 PIC 的目的：链接器无需修改代码，就能把共享库加载到任意地址运行。

课件列出四类引用情况（L2）：① 模块内的过程调用、跳转用 PC 相对偏移寻址；② 模块内数据访问（模块内全局/静态变量）；③ 模块外的过程调用、跳转；④ 模块外的数据访问（外部变量）。第②③类（跨模块）是 PIC 要重点解决的问题，通常借助 GOT（全局偏移表）和 PLT（过程链接表）实现——本课程点到为止，你只需知道"要实现动态链接，必须生成 PIC 代码"。

动态链接小结（P104）与思政点

要能辩证看待静态链接和动态链接的优缺点，针对具体需求选择合适的链接方式，建立工程思维。静态链接：程序自包含、独立运行快，但空间冗余、更新要重编；动态链接：省空间、易更新、可插件化，但运行时依赖库、有加载开销。

随堂题 · P106（错误的是）
A. 共享库在 Linux 下称 .so，Windows 下称 .dll
B. 生成的可执行目标文件是部分链接的，其中还有部分引用没有进行重定位
C. 可执行目标文件由动态链接器对可重定位目标文件和共享库中部分信息进行链接而成
D. 加载或执行时，系统调出动态链接器利用共享库对其进行动态链接
答案 C。 生成（部分链接的）可执行文件仍然是静态链接器 ld 在构建时完成的，只是把对共享库的引用保留下来；动态链接器 ld-linux.so 是在程序加载/运行时才介入完成链接的（这正是 D 所说的）。C 把两者职责和时间点搞混了。A/B/D 均正确。
随堂题 · P107（错误的是）
A. 静态库函数代码在进程代码段中，共享库函数代码不在
B. 静态库函数代码在可执行目标文件中，共享库函数代码不在
